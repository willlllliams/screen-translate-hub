## 2026-10-21

### 需求梳理

和执行人讨论后定下：

- 在现有需求和规格说明上补充，原有的大范围保留为长期目标，第一版的边界见 [第一版范围](requirements/09-v1-scope.md)；

- 显示方式两种都做、可以切换：默认按 william 演示视频里的"画在原位"，另一种是原文档里的"整屏压暗 + 译文"和"截图浮卡"；
- AI 助手按"平台把能力做成工具，pi 当大脑"的方向，门控用规则，给 jev 这类快速决策模型留接口，见 [AI 助手](spec/17-assistant.md)；
- AI 翻译源：测试时用这台电脑上 Claude Code 的无头模式调用便宜的模型，同时保留兼容 OpenAI 的接口和 Anthropic 接口；
- proposal 等这些做完再整理，过程先记在本文。

### william 旧版软件的行为（演示视频截帧）

- 快捷键（视频中为 Shift + Alt）后在屏幕上框选一块区域；
- 框内每个段落盖上一块深灰色半透明圆角底，上面是白色译文，位置和大小贴着原段落；框外不处理；
- 同一段先出现直译质量的机翻，随后被质量更好的 AI 译文替换，即竞速；
- 页面滚动后，译文停在原来的位置，与画面错开。

### 第一次端到端运行（无界面）

`tools/dev/e2e.ts` 用真实的主程序核心、Python 采集（回放画面）、OCR、归一化和运行协调器，配模拟翻译源和记录显示端：

- 单次截图：6 个段落全部识别正确、合并正确，竞速完成，显示端收到 88 个事件，序号无缺口；含服务启动和 OCR 模型加载约 4.1 s；
- 持续屏幕：回放原页、滚动、换页、翻回四帧。待处理位如需求 04 第 3.2 节所述，第三帧在处理期间被第四帧替换；滚动的批次只识别 2 块区域、复用 5 段；翻回后滚出又滚回的段落命中译文缓存。

实测发现两处复用判定的问题，已修订 spec 04 第 4.5、4.6 节：

1. 内容滚到固定标题栏底下时，被挡住的一行仍在画面之内但不再一致，原写法要求一个位移对全部行成立，连带可见的行也定位不到，旧位置被送去识别，识别区域切过新位置上的文字，得到 "OnTversations." 这样的残缺原文，并在下一批被复用；
2. 相邻一行的下伸笔画落进这一行的方块，使一两个方块在任何位移下都不一致。

改为逐行定位，每行取过半方块一致的位移。定位只决定识别区域，复用判定仍要求全部一致。

### 桌面上的第一次运行

主程序（Electron 45）在桌面会话启动，开发时经 `--dev-control` 打开的本机控制端口驱动（`tools/dev/ctl.ts`），浮层被排除在采集之外，所以另取浮层页面最后渲染的一帧，与桌面截图合成后查看（`tools/dev/compose.ts`）；`--debug-capturable` 则让浮层可被采集，用于看真实层级。

**Electron 透明窗口在这台电脑上不显示。** 用 `tools/dev/electron-probe.cjs` 对照：不透明窗口正常，透明窗口无论 GDI 还是 Windows.Graphics.Capture 都采不到，`--use-angle=warp`、`d3d11-warp` 加 DirectComposition、`--disable-gpu` 都不行。`app.getGPUFeatureStatus()` 显示 `gpu_compositing: disabled_software`：远程软件的虚拟显示器上没有 GPU 合成，Chromium 的透明窗口依赖它。远程桌面、虚拟机、部分显卡驱动下用户也会遇到同样情况，所以没有当作本机问题绕过，而是改了实现：

- 浮层页面用离屏渲染（`webPreferences.offscreen`），每帧的 BGRA 位图经 `UpdateLayeredWindow` 推进一个原生分层窗口（`WS_EX_LAYERED`，逐像素透明，`koffi` 调用 Win32），不需要 GPU；
- 分层窗口照样可以 `WS_EX_TRANSPARENT` 穿透点击、`WDA_EXCLUDEFROMCAPTURE` 排除采集，实测两者都生效；
- 框选区域的窗口改为先截整屏、在不透明的全屏窗口里显示冻结的画面，用户在上面拖框，结果从这张截图里裁出。

接着在真实桌面上发现并修正：

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 浮层页面有段落，画面上什么都没有 | 渲染器把根元素改成 `position: relative`，覆盖了页面的 `absolute; inset: 0`，根元素高度为 0 且 `overflow: hidden` | 渲染器只在根元素未定位时设定位，并按视图尺寸设根元素宽高 |
| 整屏浮层里的译文纵向错位约 6% | 窗口初始尺寸被限制在工作区（屏幕减任务栏），离屏页面只有 1366×720 | 页面加载后重新设置内容尺寸 |
| 开始持续翻译后任务栏沉到其他窗口下面 | 覆盖整块显示器的置顶窗口被系统当作全屏程序 | 浮层比显示器少一像素高 |
| 标题 "Release notes" 并进下一段 | 标题与正文的间距不到一行高，原规则只拆"两行都短"的标签 | 明显短于栏宽、下一行以新句开头时断开（spec 06 第 6 节 v1 补充） |
| Tk 窗口里相邻两段合成一段 | 段间距约 0.7 行高，小于 kg | 与本叶常见行距比较，多出 0.4 行高以上即断开 |
| 工具栏图标被识别成 "B"、"I"、"H1"、"++"，时钟、日期也被翻译 | 没有可译的词 | 不含字母或只有单个拉丁字母的段落不送翻译（需求 09 第 3.2 节） |
| "TubaWinUi3.exe - 系统警告" 盖上一块与原文一样的底板 | 译文只改了空格 | 译文与原文只差空白时不画 |
| 译文行首出现 "。" | 换行没有避头尾 | 闭合标点不放行首、开引号不放行尾 |
| 局部设置补丁冲掉了显示设置的其余字段 | 设置只做了浅合并 | 嵌套对象按键合并 |
| 跟随窗口时浮层盖住了别的置顶对话框，修正后又沉到目标窗口下面 | 插在置顶窗口之后会变成置顶；后台进程调用 `HWND_TOP` 成功但无效 | 目标在普通层最上时，先置顶再取消置顶（落在普通层最上），其余情况插在目标上方的窗口之后 |

持续模式在可控的测试窗口（`tools/dev/stage.py`）上的结果：首批 16 段竞速、7 段无词、4 段同语言；滚动 3 行后复用 22 段，只翻译新露出的 5 段；改写一段后命中缓存 5 段、新翻译 2 段；窗口移动后浮层跟到新位置。

### 局域网观看

观看服务和观看页做完后，用集成测试（`services/viewer/test/viewer.test.ts`：模拟运行协调器发布、模拟浏览器订阅，检查 Origin、访问码、画面缩放和共享关闭）和真实运行验证：桌面持续翻译整个屏幕，观看页在离屏浏览器里以手机和平板尺寸打开（`tools/dev/page-shot.cjs`）。

- 第一次真实运行时画面全黑：协调器的画面编号是 `运行:批次`，带冒号，HTTP 路由只接受字母数字和连字符。改为接受任意一段路径并解码；
- 整块 1366 像素宽的桌面缩到手机的 412 像素后，译文字号被压到最小字号，长段落只能截断。加了"列表"布局；
- 开发机上第一次启动时观看服务按默认值监听所有网络，Windows 防火墙弹出了是否允许 Node.js 的询问。这是用户的安全决定，没有替用户选择，询问框留在桌面上；之后的测试把观看服务改为只监听本机；
- Electron 在 Windows 上遇到形如网址的命令行参数会直接退出（退出码 -1，没有任何输出），截网页的工具改为从环境变量读网址。

### AI 助手

- pi 1.3.0 的 SDK 用 `createAgentSession` 的 `tools`（白名单）加 `customTools` 接入平台工具，比扩展的 `registerTool` 更直接；没有 API 密钥也能测：测试里起一个按脚本回答的 OpenAI 兼容服务，pi 先调用工具、再流式回答，确认 pi 只看到平台工具（`services/assistant/test/brain-pi.test.ts`）；
- jev 的实际接口与早先记下的不同：`@typesafe-ai/sdk` 的 `systemOne({state, questions})`，是非题（`noul`）只返回概率，没有置信度。改为同时问一个选择题，用它的置信度决定是否采信；
- Claude Code 大脑用真实的 haiku 测试（`tools/dev/try-assistant-brain.ts`）：第一轮调用 `get_context` 和 `annotate`，在给定的屏幕坐标画框，约 5 秒；第二轮记得第一轮指过的数字，约 3 秒；
- 桌面上实测：经开发控制在卡片里提问，AI 截屏、OCR，在测试窗口的标题 "Signing in" 上画了箭头；
- 发现并修正：会话开始后第一次心跳没有比较基准，被当作"整屏都变了"而多叫醒一次；AI 在调用工具前后的两段话在卡片里连成了一句；暂停期间心跳以外的叫醒（快捷键）仍会调用 AI。

### Bergamot

- npm 上的 `@browsermt/bergamot-translator` 停在 2022 年的 0.4.9，Firefox 现在的模型是 2.x 版本。改用 Firefox 自己的组合：Remote Settings 中的 WASM（3.0）加 Firefox 源码中对应的胶水代码（v0.6.0）。胶水代码在 Node 中给出 `wasmBinary` 就不读文件，可以直接在 worker 线程中运行；
- 模型集合有 742 条记录、58 种语言，大多是与英文之间的方向；中文的模型用源、目标两个词表；
- 实测（`tools/dev/try-bergamot.ts`）：英文→简体中文，下载加载约 2 秒（约 53 MB），4 段 110 毫秒；日文→简体中文经英文转译，2 段 96 毫秒；译文质量可用，但汉字之间常是半角标点，加了全角替换；
- 与 Claude Code 竞速的截图翻译：Bergamot 的译文在请求后约 2.2 秒出现（含截屏和 OCR），Claude 的译文约 5.3 秒逐步替换，与 william 演示视频中的过程一致。

## 2026-10-23

### 独立验收测试

另起一个只拿到 README、方案说明、第一版范围和开发工具说明的测试代理，让它自己定测试计划、在桌面上逐项验证。结果：自动测试和端到端运行全部通过；截图翻译、持续翻译（滚动复用、回滚命中缓存、改写只重翻一段）、显示设置、窗口模式的跟随与层级、局域网观看（访问码、锁定、手机与平板宽度、关闭共享）、AI 助手、Bergamot、历史记录、工作流文件、服务被杀后自动重启都通过。这次实测截图翻译的 Bergamot 译文约 1.2 秒出现，Claude 的译文约 3.6 秒定稿。

真实输入没能测：桌面前台一直是一个已提升权限的终端窗口，Windows 的 UIPI 会丢弃非提升进程注入的全部键盘鼠标输入（`SendInput` 返回成功但没有效果，`SetCursorPos` 失败）。能证明的是程序运行时五个快捷键都已在系统中注册、退出后释放，悬停读的是真实指针位置。

### 验收发现的问题与修正

| 问题 | 原因 | 修正 |
| --- | --- | --- |
| Claude Code 没装时，Bergamot 的译文 16 秒后变成错误标记，没有整体提示 | 可执行文件不存在时子进程只发 `error` 事件，翻译请求一直等到超时，按单段失败处理 | `error` 也结束等待，报告 `unavailable`；协调器按首选源整体不可用处理，保留 Bergamot 的译文并显示提示 |
| 宽窗口里标题并入上一段、相邻两段并成一段 | 每段只有一行时，"本叶常见行距"就是段间距本身；OCR 框高同一字号相差 20 到 25 像素，按上下边计算的间距随之波动 | 归一化第 6.1 节第 4 条：按中心距离、取较小行高计算间距，超过 0.55 行高时句末或标题断开 |
| 浮卡把宽而矮的截图拉伸 | 截图铺满浮卡，浮卡有最小高度 | 按比例放进浮卡并居中 |
| 窗口模式下原文提示框被截断 | 按固定 500 像素宽限位，覆盖层只有窗口大小 | 量实际尺寸，放不下时改到指针左侧或上方 |
| AI 大脑不知道用户的任务 | 卡片先开会话再设任务，系统提示词在开始时已定 | 新任务在下一次叫醒时放在消息前告诉模型 |
| Bergamot 是唯一翻译源时第一次翻译没有结果 | 模型不在本机就立即回答不可用 | 一个请求最多等 10 秒下载；实测空目录下 3.4 秒得到译文 |
| `%TEMP%` 下积累空目录和带过期令牌的 MCP 配置 | 每次启动新建临时目录，服务被强行结束时不删除 | Claude Code 引擎用固定目录；助手启动时清理上次遗留的会话目录 |
| 原位结果显示期间别的程序收不到 Esc | Esc 注册成了全局热键 | 改为轮询按键状态 |
| 历史文件名是 UTC 时间 | | 改用本地时间 |
| 观看页被锁定时只显示 Reconnecting… | 浏览器读不到 WebSocket 被拒的原因 | 新增 `/lockout`，页面据此提示稍后再试 |
| 开发控制改翻译源后测到的还是旧的翻译源 | 开发控制只保存设置，不重启服务 | 与设置页共用同一个应用设置的函数 |

修正后在桌面上逐项复测：Claude Code 路径错误时 Bergamot 的译文保留、19 秒后仍然没有错误标记、提示写明原因；宽窗口的 8 个段落各自分开，640 像素宽窗口里折行的段落照常合并；浮卡中的截图宽高比与原图一致；原位结果显示期间 Esc 没有被占用；窗口模式下提示框在指针左上方完整显示；AI 助手回答正常，暂停、继续、停止正常，遗留的会话目录被清理。

开发时通知的来源显示为 "Electron"：Electron 在开始菜单建了一个名为 Electron、带本程序 AppUserModelID 的快捷方式，Windows 按快捷方式的名字显示来源。打包后的程序带自己的产品名，由安装包建立快捷方式时解决，第一版不改。

### 第二轮独立测试

另一个测试代理在远端做了一轮不碰桌面的测试：用合成图片走真实 OCR、归一化、协调器和服务协议，用模拟翻译源测故障时序和负载，单独调用一次真实的 Claude haiku，并在隔离的观看服务上实际操作网页。新增 33 个场景，发现 3 个问题和一处错误分类：

| 问题 | 原因 | 修正 |
| --- | --- | --- |
| 观看服务重启后，网页一直显示 Reconnecting…，停在旧译文上 | 网页重新连上后，看到同一个来源编号就认为已经订阅；旧订阅随旧连接结束了，新连接上没有重新订阅。同一连接上来源下线又以同一编号回来（关闭再打开共享）也是这样 | 网页记下当前连接上的订阅是否还在，不在就重新订阅；同一来源重新订阅时，新快照到来前保留原来的画面 |
| 服务进程第一次没能启动（工作目录不存在），修好之后监管器也不再启动它 | 进程没能启动时只有 `error` 事件、没有 `exit`，监管器一直以为它在运行 | 两种事件共用一次性的结束处理：记为一次崩溃、按退避重试，之后 `ensure` 可以再次启动 |
| 列表布局下关掉"显示译文"，列表仍然只显示译文 | 列表绘制没有读这个设置 | 关掉时列表改为显示原文（包括本来就是目标语言的段落）；画面专用的设置（显示方式、底图、不透明度、亮度、适配）在列表布局下隐藏；字号也作用于列表 |
| 图像数据长度与宽高不符时，OCR 回的是 `internal` | 数组变形失败的异常没有归类 | 先检查长度，回 `invalid_argument` |
