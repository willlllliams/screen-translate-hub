# 规格说明总览

本文说明规格说明（specification，下文简称 spec）的范围、文档结构，以及各份 spec 文档共用的约定。

## 1 范围

需求文档规定平台要做到什么，spec 规定怎样做到：数据的精确格式、服务之间的接口、运行协调器的状态机与算法、两个桌面平台的实现方式，以及技术选型。

实现以 spec 为准。spec 与需求文档不一致时，先修订其中一方，使两者一致，再继续实现。每份 spec 文档在开头列出它对应的需求章节；需求修订时，按这份对应关系找到需要同步修改的 spec。

## 3 约定

### 3.1 规范用语

spec 中的"必须"表示实现不满足这一条就不符合 spec；"可以"表示允许、但不要求。其余叙述是说明和理由，不构成要求。

### 3.2 数据记号

spec 用下表的记号描述数据字段。字段在线路上怎样编码，见 08 服务协议。

| 记号 | 含义 |
| --- | --- |
| `string` | Unicode 文本，按 Unicode 规范化形式 C（Normalization Form C，NFC）规范化，传输时用 UTF-8 编码 |
| `bool` | 真或假 |
| `int32`、`int64` | 有符号整数 |
| `uint32`、`uint64` | 无符号整数 |
| `float32`、`float64` | IEEE 754 浮点数 |
| `bytes` | 字节序列 |
| `T?` | 可以缺省的字段 |
| `list<T>` | 有序列表 |
| `map<K, V>` | 键值表，键不重复 |
| `enum{a, b}` | 取值限于列出的几项 |

字段名只用小写字母、数字和下划线，例如 `batch_seq`。

### 3.3 标识

| 标识 | 格式 | 唯一范围 |
| --- | --- | --- |
| 设备、工作流、运行、历史条目 | UUID 第 7 版（RFC 9562），小写、带连字符 | 全局 |
| 服务 | 登记名称，由小写字母、数字、点和连字符组成 | 一台设备内；服务实例由设备标识加登记名称确定（08 服务协议 8.1） |
| 批次 `batch_seq` | `uint64`，由运行协调器编号，从 1 开始，每个批次加一 | 一次运行内 |
| 段落 `paragraph_id` | `uint32`，从 1 开始 | 一个批次内 |
| 节点 `node_id` | 由小写字母、数字、下划线和连字符组成，长 1 至 64 个字符 | 一条工作流内 |

UUID 第 7 版的前 48 位是毫秒时间戳，标识按字典序排列就是按生成时间排列，历史记录和运行记录可以直接用标识分页。

一个段落由运行、批次、段落三项标识共同确定，与需求文档 [OCR 与竞速翻译](../requirements/03-ocr-and-translation-race.md) 3.5 一致。

### 3.4 时间

时间有两种用途，分别处理：

- 墙上时间用于记录和显示，格式为 RFC 3339 的 UTC 时间，精确到毫秒，例如 `2026-10-14T08:00:00.123Z`；
- 时长和时限用单调时钟计算，单位为毫秒。单调时钟不受用户修改系统时间的影响。

跨设备传递时限时，传递剩余时长，不传递时刻。两台设备的墙上时间可能相差数秒，按时刻传递会让接收方算错时限。

接收方收到剩余时长 $r$ 时，记下自己单调时钟的读数 $t_{\mathrm{recv}}$，本地时限取：

$$
t_{\mathrm{local}} = t_{\mathrm{recv}} + r
$$

设发送方在单调时刻 $t_{\mathrm{send}}$ 发出消息，此时它的时限为 $t_{\mathrm{send}} + r$。消息在路上耗时 $\ell$，接收方的本地时限因此比发送方的时限晚 $\ell$。发送方按自己的时限独立结束任务，接收方晚交回的结果按 [运行协调器](04-run-coordinator.md) 的有效性规则丢弃，所以这段误差只会多占用接收方一小段计算时间，不影响显示的正确性。

### 3.5 语言标识

语言用 BCP 47 语言标签（RFC 5646）表示，例如 `en`、`ja`、`ko`、`ar`、`zh-Hans`、`zh-Hant`。中文必须标明简体或繁体，因为 OCR 引擎和翻译引擎对两者的支持各不相同。

源语言可以取特殊值 `auto`，表示自动检测，规则见需求文档 [产品需求](../requirements/01-product.md) 第 7 节。

服务声明支持的语言时使用同样的标签。判断服务是否支持某种语言 $T$，按以下步骤：

1. 统一大小写：语言子标签小写，文字子标签首字母大写，地区子标签大写；
2. 服务声明的列表中有 $T$，即支持；
3. 否则从 $T$ 的末尾去掉一个子标签，回到第 2 步，直到只剩语言子标签为止。

这是 RFC 4647 第 3.4 节"查找"的做法。引擎常给出带地区的标签，例如 `zh-Hans-CN`、`en-US`；按这个规则，`zh-Hans-CN` 依次与 `zh-Hans`、`zh` 比较，声明了 `zh-Hans` 的服务被判为支持。去掉子标签只朝更宽的方向进行，声明了 `zh-Hans-CN` 的服务不会因此被判为支持 `zh-Hans`。

### 3.6 接口版本

接口版本写作"主版本.次版本"，例如 `1.3`。主版本变化表示不兼容的修改，次版本变化只增加可以忽略的内容。

记服务实现的版本为 $(M_s, m_s)$，调用方要求的版本为 $(M_c, m_c)$。服务满足调用方，当且仅当：

$$
M_s = M_c \quad \text{且} \quad m_s \geq m_c
$$

例如，调用方要求 `1.2`，实现了 `1.3` 的服务满足要求，实现了 `1.1` 或 `2.0` 的服务不满足。检查发生在哪些时刻，见 08 服务协议。

### 3.7 待定的默认值

标注"默认值待定"的参数，spec 给出名称、单位和取值范围，默认值在原型阶段实测后填入，对应 [待定事项](../requirements/open-questions.md) 第 2 节。
