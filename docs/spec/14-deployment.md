# 部署与运维

对应需求：[产品需求](../requirements/01-product.md) 第 2.2、2.4、2.5 节，[服务拆分](../requirements/06-services.md) 第 3.3 节，[账号、设备与共享](../requirements/05-accounts-devices-sharing.md) 第 2、7 节，[桌面平台](../requirements/07-desktop-platforms.md) 第 8 节。

本文规定后台的组成、首次部署、证书、透传中转、升级、备份与恢复、出站代理，以及桌面端的发行方式。

## 1 部署方式

| 部署方式 | 条件 | 证书 |
| --- | --- | --- |
| 公网服务器 | 服务器有域名，或者只有公网地址 | 由 Caddy 自动申请，见第 4 节 |
| 家庭部署加透传中转 | 后台在家里，部署者另有一台公网服务器，并有一个域名 | 由家里的 Caddy 经中转申请，见第 5 节 |
| 离线版 | 没有服务器 | 不部署后台，桌面端独立使用（需求 01 第 2.2 节） |

家庭部署必须有域名：透传中转按 TLS 握手中的服务器名称选择转发目标，用地址直接访问时握手中没有服务器名称，中转无从转发。

## 2 后台的组成

后台用一份编排文件启动，编排文件只使用 Compose 规范中的功能，可以用 Docker Engine 或其他兼容 Compose 的工具运行，不依赖 Docker Desktop（需求 06 第 3.3 节）。

| 容器 | 镜像 | 职责 | 持久数据 |
| --- | --- | --- | --- |
| `ingress` | 以固定版本的 Caddy 官方镜像为基础、内含三份 Caddyfile 模板的项目镜像，Caddy 不低于 2.11.4（第 4.2 节） | 网关、证书 | 证书 |
| `hub` | 项目镜像 | 设备连接与中转 | 无 |
| `auth` | 项目镜像 | 账号与认证 | `auth.db` |
| `registry` | 项目镜像 | 服务注册 | `registry.db` |
| `viewer` | 项目镜像 | 观看分发 | 无 |
| `web` | 项目镜像 | 网页前端 | 无 |
| `config` | 项目镜像 | 工作流与配置存储 | `config.db` |
| `history` | 项目镜像 | 历史记录存储 | `history.db` 和文件 |
| `coordinator` | 项目镜像 | 运行协调器 | 无 |
| `normalize` | 项目镜像 | 归一化 | 无 |
| `ocr` | 项目镜像，内含 PP-OCRv6 medium 和 PP-OCRv5 的韩文、阿拉伯文识别模型 | OCR | 无 |
| `translate` | 项目镜像 | 翻译服务，按 Hy-MT2 的提示词格式调用 llama-server | 无 |
| `llama` | 以 llama.cpp 官方镜像为基础、加入 Hy-MT2-1.8B 模型的项目镜像 | 运行翻译模型 | 无 |
| `ai` | 项目镜像 | AI 适配服务。默认启动，主人配置 AI 服务之前不登记任何服务 | 无 |
| `http` | 项目镜像 | 自定义 HTTP 请求。默认启动，只执行主人工作流中的请求 | 无 |
| `frpc` | 以 frp 官方发布的程序构建的项目镜像 | 家庭部署时连接透传中转 | 无 |
| `llama-gpu` | 以 llama.cpp 官方带 CUDA 的镜像为基础、加入 Hy-MT2-7B 模型的项目镜像 | 在显卡上运行翻译模型 | 无 |
| `translate-gpu` | 与 `translate` 相同的镜像，连接 `llama-gpu` | 作为另一项翻译服务登记 | 无 |
| `ocr-vl` | 运行 PaddleOCR-VL、实现 `ocr` 接口的项目镜像 | 可选的 OCR 服务，适合双栏论文和复杂文档（[技术选型](15-tech-selection.md) 6.3） | 无 |

规则：

- 全部项目镜像都同时提供 linux/amd64 和 linux/arm64（需求 06 第 3.3 节），`gpu` 配置组的镜像除外：它们只提供上游有显卡版本的架构，并在登记时声明（需求 06 第 3.3、5 节）；
- 只有 `ingress` 对外开放端口：443，以及用于 HTTP-01 质询和跳转到 HTTPS 的 80。其余容器只在编排的内部网络中通信；
- 有状态的容器各自挂载自己的数据卷，数据卷放在本地磁盘上（[后台平台服务](10-backend.md) 1.1）；
- 各服务的服务凭据由第 3 节的初始化命令生成，经 Compose 的机密配置以只读文件交给容器（[安全](11-security.md) 第 4 节）；
- 编排文件默认一次启动全部服务（需求 01 第 2.2 节），两个可选配置组（profile）除外，由第 3 节的初始化命令按部署者的回答写入配置文件：
  - `relay`：只含 `frpc`，用于家庭部署加透传中转；
  - `gpu`：含 `llama-gpu`、`translate-gpu` 和 `ocr-vl`，用于有 NVIDIA 显卡的服务器（需求 01 第 9 节）。这几个容器经 Compose 规范的设备预留（`deploy.resources.reservations.devices`）使用显卡，服务器要装好 NVIDIA 驱动和 NVIDIA Container Toolkit。没有启用 `gpu` 时，后台只有 CPU 上的 `translate` 和 `ocr`；
- 模型直接放进镜像。Hy-MT2 和 PP-OCR 的模型都是 Apache-2.0，可以随镜像分发，镜像中附带模型的许可文件（[技术选型](15-tech-selection.md) 第 12 节）。升级模型就是升级镜像，与需求 01 第 2.4 节"拉取新的容器镜像升级"一致。

每个项目镜像内的服务都提供一个只在内部网络中监听的健康检查接口，编排文件据此配置健康检查。

## 3 首次部署

1. 准备一台 Linux 服务器，安装 Docker Engine 或其他兼容 Compose 的工具。公网服务器使用域名时，把域名解析到这台服务器的公网地址；家庭部署时，域名解析到中转服务器（第 5.1 节）。服务器有 NVIDIA 显卡、要启用 `gpu` 配置组时，装好显卡驱动和 NVIDIA Container Toolkit；
2. 从项目的发布页下载部署包：编排文件、配置模板、frps 的配置模板和管理命令；
3. 运行初始化命令 `sth-admin init`。它依次询问：
   1. 部署方式：公网服务器，或者家庭部署加透传中转；
   2. 域名或公网地址，以及证书通知邮箱。家庭部署必须填域名（第 1 节）；
   3. 家庭部署时，中转服务器的地址、frps 接受 frpc 连接的端口和令牌；
   4. 服务器有没有可用的 NVIDIA 显卡。

   然后生成后台的设备标识和各服务的服务凭据，按回答选定第 4 节的一份 Caddyfile 模板，写出配置文件；家庭部署时另外写出 frpc 的配置，在配置文件中启用 `relay`；有显卡时启用 `gpu`。部署者不需要手动修改任何文件；
4. 启动编排：`docker compose up -d`；
5. 创建主人账号：`docker compose exec auth sth-admin create-owner`，按提示设置账号和密码。在此之前，网页端只显示"请先在服务器上创建账号"（[后台平台服务](10-backend.md) 3.2）；
6. 用浏览器打开后台的地址登录，建议立即开启二步验证，再生成配对码接入电脑。

部署说明要求服务器开启磁盘加密（需求 05 第 7 节）。

主人忘记密码或丢失验证器时，部署者在服务器上重置（需求 05 第 2 节，[安全](11-security.md) 2.5）：

| 命令 | 作用 |
| --- | --- |
| `docker compose exec auth sth-admin reset-password` | 按提示设置新密码，二步验证和恢复码保持不变 |
| `docker compose exec auth sth-admin reset-2fa` | 关闭二步验证，删除全部恢复码，主人登录后可以重新开启 |

两条命令都在 `auth` 容器中直接修改 `auth.db`，与 `create-owner` 相同，不违反"每个服务独占自己的数据"；执行后全部会话立即失效，已经建立的连接随即断开（[后台平台服务](10-backend.md) 3.2）。

## 4 证书

### 4.1 有域名

Caddy 为域名自动申请和续期证书，HTTP-01 和 TLS-ALPN-01 两种质询默认都启用（[技术选型](15-tech-selection.md) 第 5 节）。服务器的 80 和 443 端口都要能从公网访问。

### 4.2 只有公网地址

Let's Encrypt 从 2026-01-15 起正式签发 IP 地址证书，规则如下：

- 只在 `shortlived` 证书配置下签发，有效期约 160 小时，必须自动续期；
- 只能用 HTTP-01 或 TLS-ALPN-01 质询验证地址，不能用 DNS-01；
- 同时支持 IPv4 和 IPv6。

Caddy 在 ACME 签发者中用 `profile shortlived` 选择这个证书配置，社区记录显示 2.11.4 起可以取得 IP 地址证书；这个选项在 Caddy 中仍标为实验性。浏览器按地址访问时不发送服务器名称，Caddy 的配置因此用 `default_sni` 指定这个地址，让这类连接使用 IP 地址证书。

`ingress` 镜像内含三份 Caddyfile 模板，初始化命令按部署方式和填写的内容选定一份：

| 模板 | 适用情况 | 要点 |
| --- | --- | --- |
| 域名 | 公网服务器，有域名 | HTTP-01 和 TLS-ALPN-01 两种质询都启用（4.1） |
| 公网地址 | 公网服务器，只有公网地址 | `profile shortlived`，`default_sni` 指定这个地址（4.2） |
| 家庭部署 | 家里的后台，经透传中转访问 | 关闭 HTTP-01，只用 TLS-ALPN-01；在 TLS 之前解析 PROXY 协议头，只接受来自 `frpc` 所在内部网络的头（第 5.2 节） |

模板中的域名、地址和邮箱取自配置文件，Caddy 启动时读入，升级 `ingress` 镜像不会覆盖部署者的配置。

## 5 透传中转

### 5.1 中转服务器

部署者在有公网地址的服务器上运行 frp 的服务端 frps（[架构](01-architecture.md) 第 4 节）：

- frps 在公网 443 端口接受访问者的连接，按 TLS 握手中的服务器名称转发；
- frps 在另一个端口接受家里 frpc 的连接，frpc 与 frps 之间使用令牌认证，连接本身使用 TLS；
- 域名的 A 记录指向这台服务器。域名如果有 AAAA 记录，同样指向这台服务器，并且 frps 监听 IPv6：Let's Encrypt 有 IPv6 地址时优先用 IPv6 连接，只有连接超时才退回 IPv4（[技术选型](15-tech-selection.md) 第 5 节）。

部署包提供 frps 的配置模板和启动脚本。中转服务器上只运行 frps，不保存任何画面、译文和证书私钥。

### 5.2 家里的后台

家里的后台启用 `relay` 配置组中的 `frpc` 容器，使用第 4 节的"家庭部署"Caddyfile 模板，两者都由初始化命令写入配置（第 3 节）：

- frpc 主动连接中转服务器，代理类型为 `https`，域名为部署者的域名，转发目标是内部网络中的 `ingress` 的 443 端口；
- frpc 用 PROXY 协议第 2 版传递访问者的真实地址。Caddy 在 TLS 之前解析 PROXY 协议头，并且只接受来自 `frpc` 容器所在内部网络的 PROXY 协议头，防止其他来源伪造访问者地址。登录限速按来源地址计数（[安全](11-security.md) 2.2），真实地址因此是必需的；
- 家里的 80 端口不对外开放，Caddy 的配置关闭 HTTP-01 质询，只用 TLS-ALPN-01。

证书的申请过程：证书颁发机构连接域名的 443 端口，即中转服务器；frps 按服务器名称把这条连接原样转给 frpc，再到家里的 Caddy；Caddy 完成 TLS-ALPN-01 质询。中转只搬运密文，证书私钥始终在家里（需求 01 第 2.2 节）。

## 6 升级

### 6.1 后台

后台用管理命令 `sth-admin upgrade 版本号` 升级（需求 01 第 2.4 节）。编排文件中全部项目镜像的版本号来自配置文件中的同一个变量，`ingress` 也是项目镜像，Caddy 的版本随之一起升级和回滚。升级命令依次执行：

1. 记下当前的版本号；
2. 把配置文件中的版本号改为新版本，拉取新的镜像；
3. 重新启动编排。各服务启动时自动备份并升级自己的数据库结构（[后台平台服务](10-backend.md) 1.3）；
4. 等待各服务的健康检查通过；
5. 有服务在限定时间内（默认值待定）没有通过健康检查时，自动回滚：
   1. 停止编排，把版本号改回第 1 步记下的值；
   2. 数据库结构已经升级成功的服务，把本次升级时它在 `backups/` 中生成的备份复制回原位。备份按文件名中的服务名、时刻和原结构版本选取（[后台平台服务](10-backend.md) 1.3）。数据库结构升级失败的服务已经在事务中回滚，不需要恢复；
   3. 重新启动编排。

   旧版本的服务读到比自己新的结构版本时以错误退出，不读写数据库（[后台平台服务](10-backend.md) 1.3），所以恢复必须在启动之前完成，由升级命令负责。

部署者不需要手动修改编排文件。回滚后，命令输出失败的服务和它的日志位置。

各服务也可以单独升级。接口的次版本只增加可以忽略的内容（[总览](00-overview.md) 3.6），新旧版本的服务可以同时运行；主版本变化时，发布说明列出必须一起升级的服务。

### 6.2 桌面端与后台的版本

桌面端连上后台时，握手先协商协议版本（[服务协议](08-service-protocol.md) 第 3 节），之后每次调用检查接口版本（服务协议第 11 节）。协议的主版本不兼容时，握手失败，较旧的一方提示用户升级，这期间桌面端按独立使用的方式工作（需求 01 第 2.4 节）。

## 7 备份与恢复

后台提供两条管理命令（需求 01 第 2.4 节）：

| 命令 | 作用 |
| --- | --- |
| `sth-admin backup 目录` | 在服务运行时做一次完整备份 |
| `sth-admin restore 目录` | 从一次备份恢复 |
| `sth-admin restore-db 服务名 备份文件` | 用这个服务 `backups/` 中的一份升级前备份恢复它的数据库，用于升级成功、但数据被改错的情况（[后台平台服务](10-backend.md) 1.3）。命令先停止这个服务，替换数据库，再启动它 |

备份的内容和方法：

| 内容 | 方法 |
| --- | --- |
| `auth.db`、`registry.db`、`config.db`、`history.db` | 管理命令在各服务自己的容器中运行备份程序，用 SQLite 的在线备份接口把数据库复制到备份目录。备份程序与服务来自同一个镜像，属于这个服务的一部分，不违反"每个服务独占自己的数据"。在线备份遇到写入会从头重来，备份程序按 SQLite 文档的做法分步执行，每步之间短暂停顿，让写入频繁时备份也能完成 |
| 历史记录的文件 | 在数据库备份完成之后复制。文件写入后不再修改，复制时新增的文件没有对应的数据库记录，恢复后作为孤立文件被定期清理（[后台平台服务](10-backend.md) 8.2） |
| 配置文件和服务凭据 | 直接复制 |

证书不在备份范围内：恢复后 Caddy 会重新申请。

备份中有明文的历史截图、外部服务凭据和服务凭据，所以备份目录必须位于加密的存储上，部署说明同样提醒（需求 05 第 7 节）。后台不对历史记录做应用层加密的依据是数据只放在加密的磁盘上，备份写到外接盘、网络存储或网盘时，同样要满足这一条。

恢复时，管理命令停止全部服务，用备份替换数据库和文件，再启动服务。备份来自旧版本时，服务启动时按 [后台平台服务](10-backend.md) 1.3 自动升级数据库结构；备份来自更新的版本时，服务以错误退出，管理命令提示先把后台升级到不低于备份的版本。历史记录存储启动时删除文件缺失的条目，即备份进行期间被删除的那些（[后台平台服务](10-backend.md) 8.2）。

## 8 出站代理

外部 AI 和翻译服务的网络条件各不相同（需求 01 第 2.5 节）：

- 后台：配置文件中设置全局代理，支持 HTTP 和 SOCKS5，交给会访问外部网络的容器，即 `ai` 和 `http`。翻译服务只调用内部网络中的 `llama`、`llama-gpu`，不访问外部网络；外部翻译接口经自定义 HTTP 接口节点接入（[服务接口](09-service-interfaces.md) 第 15 节）。内部网络中的地址不经代理；
- 后台的每个外部服务可以在网页端的服务设置中覆盖全局设置，单独指定走代理或直连；`ai` 和 `http` 经 `config.WatchServiceSettings` 取得这些设置（[服务接口](09-service-interfaces.md) 第 20 节）；
- 桌面端：默认跟随系统的代理设置，也可以单独设置 HTTP 或 SOCKS5 代理，每个外部服务可以单独覆盖；检查更新和下载安装包同样经代理（[桌面端](12-desktop.md) 2.6）。
