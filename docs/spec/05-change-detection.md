# 变化检测

对应需求：[运行与生命周期](../requirements/04-run-lifecycle.md) 第 3.2、3.5、6、8.3 节，[工作流](../requirements/02-workflow.md) 第 4.1 节，[服务拆分](../requirements/06-services.md) 第 3.1 节。

变化检测由源电脑上的屏幕采集服务完成（需求 06 第 3.1 节）。比对和变化图的算法写成一个与平台无关的库，Windows 和 macOS 的屏幕采集服务、以及测试用的回放采集，都链接同一个库。本文规定采集会话中与变化检测有关的状态、截图的接受规则、待处理位、变化图的计算方法和开销。变化图的数据结构见 [数据模型](02-data-model.md) 第 7 节，运行协调器怎样使用变化图见 [运行协调器](04-run-coordinator.md) 第 4 节。

## 1 会话

每个持续屏幕运行在屏幕采集服务中有一个采集会话，会话保存四项与变化检测有关的状态：

| 状态 | 记号 | 含义 |
| --- | --- | --- |
| 参照画面 | $F_{\mathrm{ref}}$ | 判断新截图是否变化时比对的画面 |
| 待处理位 | $F_{\mathrm{pend}}$ | 最多一张，等待成为下一个批次 |
| 上一批次画面 | $F_{\mathrm{batch}}$ | 最近一个批次的画面，用来计算变化图 |
| 画面编号 | $n$ | 最近一张成为批次的画面的 `frame_id`，会话内从 1 开始递增 |

批次序号由运行协调器编号（[运行协调器](04-run-coordinator.md) 3.1），采集会话只给画面编号。会话重新打开后，画面编号从 1 重新开始，运行协调器的批次序号不受影响。

会话支持五项操作：

| 操作 | 调用方 | 作用 |
| --- | --- | --- |
| 打开 | 运行协调器 | 建立会话，按屏幕输入节点的参数和运行开始时选定的采集范围开始采集 |
| 取批次 | 运行协调器 | 见第 3 节 |
| 暂停 | 运行协调器 | 停止采集，清空 $F_{\mathrm{pend}}$ 和 $F_{\mathrm{ref}}$，保留 $F_{\mathrm{batch}}$ |
| 恢复 | 运行协调器 | 重新开始采集 |
| 关闭 | 运行协调器 | 停止采集，丢弃全部状态 |

屏幕采集在平台之外被中止时，按原因分别处理（需求 04 第 8.3 节）：

- 用户在 macOS 菜单栏结束了采集：屏幕采集服务报告 `USER_STOPPED`，运行协调器按暂停处理；
- 采集范围是固定的窗口，这个窗口被关闭：报告 `TARGET_CLOSED`，运行协调器停止运行；采集的显示器被移除时同样停止，原因为 `DISPLAY_REMOVED`；
- 跟随活动窗口时，当前窗口被关闭：不报告，屏幕采集服务等下一个前台窗口出现后改为采集它。新窗口的第一张截图与参照画面尺寸不同时，按第 2 节被接受，变化图按画面尺寸改变处理，整张重新识别。

## 2 接受截图

### 2.1 规则

每张新截图 $F$ 到达时：

```text
procedure on_capture(F):
    if F_ref 为空 or differs(F, F_ref):
        F_pend ← F            -- 替换待处理位中原有的截图
        F_ref ← F
    -- 否则丢弃 F
```

`differs` 判断两张画面是否有变化：两张画面尺寸不同，或者存在一个像素，它在 R、G、B 某个通道上的差的绝对值大于容差 $\tau$（需求 04 第 3.2 节）。

$F_{\mathrm{ref}}$ 为空有两种情况：运行开始后的第一张截图，以及暂停恢复后的第一张截图。这两张截图一律被接受（需求 04 第 3.2 节）。

### 2.2 参照画面就是最近一张被接受的画面

需求 04 第 3.2 节规定：参照画面取最近一张被接受的画面，待处理位中有截图时取这张截图，否则取最近一个批次的画面。上面的规则满足这一条，证明如下。

$F_{\mathrm{ref}}$ 只在接受截图时改变，而接受时 $F_{\mathrm{pend}}$ 和 $F_{\mathrm{ref}}$ 被设为同一张截图，所以 $F_{\mathrm{ref}}$ 始终是最近一张被接受的画面。这张画面此刻要么还在待处理位中，要么已经被取批次操作移为 $F_{\mathrm{batch}}$；两种情况分别对应需求中的两种取法。暂停时三者被清空或保留的方式见第 1 节，恢复后的第一张截图重新建立 $F_{\mathrm{ref}}$。

需求中列出的两个反例都由这条规则处理：

- 画面缓慢渐变时，$F_{\mathrm{ref}}$ 停在最近一张被接受的画面上，不随每张被丢弃的截图移动，累积的色差最终超过容差；
- 屏幕从 A 变到 B 再回到 A 时，B 被接受，$F_{\mathrm{ref}} = B$；回到 A 的截图与 B 不同，被接受并替换待处理位中的 B。

### 2.3 开销

画面没有变化时，`differs` 要比对全部像素才能下结论，这是接受截图的最坏情况；画面有变化时，比对在遇到第一个超出容差的像素时结束。

原型实测，单线程 JavaScript 实现在 Intel Core Ultra 7 270K Plus 上比对两张相同的 3840×2160 画面，中位数为 9.4 毫秒。截屏间隔为 500 毫秒时，这项开销约占一个处理器核心的 2%。需求 04 第 3.5 节记录的逐字节比对为 2.8 毫秒，按容差比对每个像素要多做几次减法和比较，所以慢于逐字节比对。正式实现用 Rust 编写，开销在原型阶段重新测量。

### 2.4 用系统提供的脏区域缩小比对范围

两个平台的采集接口都能随画面提供"与上一帧相比变化了的区域"，即脏区域，但提供的条件不同：

- macOS：ScreenCaptureKit 的每一帧附带 `dirtyRects`（macOS 12.3 起），文档定义为重绘矩形与移动矩形之并。显示内容没有变化时，帧状态为 `idle`，系统不产生新的画面，变化检测也就不需要比对；
- Windows：Windows.Graphics.Capture 的 `DirtyRegions` 和 `DirtyRegionMode` 从 Windows 11 24H2（SDK 10.0.26100）起才有，官方文档没有说明它们的语义。更早的 Windows 11 版本只能全部比对。

两个平台的文档都没有写明脏矩形的单位和原点，使用前在原型中确认，接口细节见 12 桌面端。变化检测可以只在脏区域内比对，前提是满足以下条件：

> 从 $F_{\mathrm{ref}}$ 被采集的那一帧起，到当前帧为止，系统报告的全部脏区域之并，覆盖了这段时间内所有发生变化的像素。

截屏按定时触发时，变化检测只处理其中一部分帧，但系统对每一帧都报告脏区域。会话必须累积每一帧的脏区域，包括没有被处理的帧，才能满足上面的条件。平台不提供脏区域、累积中断，或者无法确认系统的报告完整时，退回全部比对。

## 3 取批次

运行协调器在一个批次结束后取下一个批次（[运行协调器](04-run-coordinator.md) 3.1）：

```text
procedure take_batch(wait):
    等待，直到 F_pend 非空，或者等待时长达到 wait
    if F_pend 为空: return 空
    F ← F_pend; F_pend ← 空
    M ← change_map(F, F_batch)      -- 第 4 节；F_batch 为空时 M 为空
    n ← n + 1; F_batch ← F
    return (F, M, n)                -- n 为这张画面的 frame_id
```

取批次之后 $F_{\mathrm{ref}} = F_{\mathrm{batch}} = F$，与 2.2 的结论一致。

变化图只在取批次时计算。被接受的截图多于批次：例如截屏间隔 0.5 秒、一个批次 2 秒、画面持续变化时，四张被接受的截图中只有一张成为批次（需求 04 第 3.3 节）。只为成为批次的画面计算变化图，其余三张只做 2.1 的比对。

## 4 变化图的计算

计算新画面 $N$ 相对旧画面 $O$ 的变化图分五步。两张画面尺寸不同时跳过全部步骤，直接得到全部为变化的变化图（数据模型第 7 节）。

### 4.1 零位移比对

对每个方块，逐像素比对 $N$ 与 $O$ 在同一位置的像素，得到第 0 位。比对在遇到第一个超出容差的像素时结束，所以变化的方块比不变的方块算得快。

### 4.2 变化方块的连通块

在方块网格上，求第 0 位为 0 的方块的八连通块。每个连通块大致对应一块发生变化的界面区域：滚动的内容区、刷新的面板、改变的一个数字。

### 4.3 估计位移

对面积不少于 4 个方块的连通块，先估计垂直位移，按 4.4 检验；检验后这个连通块中仍有超过 20% 的方块无法解释，再估计水平位移。面积更小的连通块只是局部的小改动，例如一个数字变了，不做估计。

先垂直、后水平的顺序依据第 5 节的测量：文档、网页和聊天窗口的滚动以垂直方向为主，垂直位移通常已经解释了绝大部分变化；水平估计要按列计算哈希，逐列访问内存，比按行慢得多，只在需要时才做。

垂直位移的估计方法：

1. 取连通块外接矩形的列范围 $[x_0, x_1)$；
2. 对 $O$ 的每一行，计算这一行在 $[x_0, x_1)$ 内像素的哈希值，建立"哈希值 → 行号列表"的索引；
3. 对 $N$ 在连通块行范围内的每一行，计算同样的哈希值，在索引中查找相同哈希值的 $O$ 的行 $y'$，为位移 $d_y = y - y'$ 投一票；
4. 得票最多的非零 $d_y$ 是这个连通块的垂直位移估计。

两类行不参与投票：

- 全部像素相同的行，例如空白行。它与 $O$ 中所有空白行都相同，会给大量错误的位移投票；
- 在 $O$ 中出现超过 8 次的行，例如表格的横线。它同样无法指出唯一的位移。

得票数少于 3，或者少于参与投票的行数的 20% 时，认为没有找到位移。水平位移按行列互换的同一方法估计：取连通块外接矩形的行范围，对每一列计算哈希。

哈希比较要求像素完全相同，不考虑容差。整像素滚动时，被移动的内容逐像素不变，可以匹配；带插值的平滑滚动或缩放会改变像素，估计失败，这块区域按变化处理，重新识别。估计失败只会多做一些 OCR，不会把变化了的内容当作未变，因为 4.4 的检验仍按容差逐像素进行。

### 4.4 检验候选位移

把各连通块估计出的位移合并去重，得到候选位移。对每个候选位移 $d_k$，在估计出它的连通块的方块外接矩形内，向外扩展一个方块，逐块检验第 $k$ 位：按数据模型第 7 节的定义，逐像素比对 $N(x, y)$ 与 $O(x - d_x^k,\ y - d_y^k)$。

检验范围包括第 0 位已经为 1 的方块。滚动段落周围的空白方块在零位移下也一致，只有它们的第 $k$ 位同样为 1，段落才会被判为整体平移（[运行协调器](04-run-coordinator.md) 4.3）。

### 4.5 排序与截断

候选位移按支持面积从大到小排列：支持面积指第 $k$ 位为 1、第 0 位为 0 的方块数，即这个位移解释了多少原本判为变化的区域。排在前 7 位的候选位移依次成为第 1 至第 7 个位移，其余舍弃。

变化图每块只有一个字节，所以位移最多 8 个，含零位移。被舍弃的位移所在的区域按变化处理，结果只是多识别几块区域，不会把变化了的内容当作未变。

### 4.6 变化面积比例

全部位检验完成后，字节为 0 的方块属于变化区域，它们的面积之和除以画面面积，得到 `changed_ratio`。

这个比例在扣除了平移区域之后计算。文档向下滚动了半屏时，零位移下约一半的方块不一致，但滚动解释了其中绝大部分，`changed_ratio` 只剩新滚入的几行，运行协调器因此不会因为滚动而整张重新识别。

## 5 开销

用一张合成的 3840×2160 画面测量 4.1 至 4.4 的开销。画面左侧是 300 像素宽的侧栏，上方是 120 像素高的工具栏，其余是文字内容区；新画面中内容区向上滚动 37 像素，工具栏中有一个 10×14 像素的字符改变，另有 2000 个像素带有容差以内的色差。方块边长 $t = 16$，容差 $\tau = 8$。单线程 JavaScript 实现，在 Intel Core Ultra 7 270K Plus 上运行，取中位数：

| 步骤 | 耗时 |
| --- | --- |
| 零位移比对，32400 个方块 | 4.4 毫秒 |
| 变化方块的八连通块 | 0.6 毫秒 |
| 最大连通块的垂直位移估计 | 19.1 毫秒 |
| 最大连通块内检验候选位移 | 5.0 毫秒 |
| 完整计算一次变化图，按 4.3 先垂直、后水平 | 33.9 毫秒 |
| 对照：每个连通块都估计垂直和水平两个方向 | 71.7 毫秒 |

完整计算包括全部 10 个连通块中面积不少于 4 个方块的那些，以及它们的检验。前四行是其中各步骤单独测得的耗时。

结果：

- 零位移下 54.8% 的方块不一致，分属 10 个连通块；
- 位移估计得到 $d_y = -37$，与实际滚动一致，参与投票的 1006 行全部投给了这个位移；
- 检验候选位移后，仍不一致的方块只剩 1.4%，即新滚入的几行和改变的字符；容差以内的色差没有被当作变化。

一次变化图的计算约 34 毫秒，只在取批次时发生一次。对照一行说明了 4.3 的顺序为什么先垂直、后水平：两个方向都估计时耗时翻倍，而这个场景中水平估计没有找到任何位移。

位移估计是最慢的一步：它对旧画面整个高度上的每一行计算哈希，处理的像素数是连通块宽度乘以画面高度。滚动可以达到整屏的距离，搜索范围不宜缩小，所以接受这项开销。正式实现用 Rust 编写，开销在原型阶段重新测量。

## 6 参数

变化检测使用两个运行参数，见 [工作流定义](03-workflow.md) 第 7 节：

- 容差 $\tau$：越大越能吸收渲染差异，但也越容易漏掉低对比度的文字变化；
- 方块边长 $t$：取值 8、16 或 32。方块越小，变化图越精细，段落因为附近一个无关像素的变化而不能复用的情况越少；代价是方块数按 $1/t^2$ 增长，变化图更大，逐块处理的固定开销更多。

两者的默认值待定，在原型阶段用验收样本实测后确定。
