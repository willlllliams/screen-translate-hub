# 桌面平台

本文规定桌面端在 Windows 和 macOS 上的平台要求：支持哪些系统版本，各项需求依赖哪些系统能力，系统权限带来哪些限制，怎样安装分发，以及两个平台之间无法消除的差异。

两个版本的功能和验收标准相同，见 [产品需求](01-product.md) 第 3 节。依赖桌面接口的部分属于系统集成服务，两个平台各有一份实现，对外接口相同，见 [服务拆分](06-services.md) 3.1。本文列出的系统接口是可行性依据，具体用法在 spec 阶段确定。

## 1 支持的系统

| 平台 | 最低版本 | 处理器 |
| --- | --- | --- |
| Windows | Windows 11 | x64；Arm 电脑通过系统仿真运行 x64 版本 |
| macOS | macOS 15 Sequoia | 只支持 Apple 芯片 |

### 1.1 Windows

Windows 版只支持 Windows 11，依据有两条：

- Windows 10 已在 2025-10-14 终止支持，个人用户的扩展安全更新延长到 2027-10-12，并且只覆盖 22H2；
- 屏幕采集时，系统会在被采集的窗口或显示器周围画一圈黄色边框。去掉边框的接口从 build 20348 起提供，Windows 10 客户端最高只到 19045，只有 Windows 11 能去掉这圈边框，见 5.1。

平台依赖的两项采集能力，`WDA_EXCLUDEFROMCAPTURE` 和 `IsCursorCaptureEnabled`，都从 Windows 10 2004 起提供，Windows 11 的各个版本都具备。

Windows 版只构建 x64 版本。Windows 11 on Arm 能仿真运行 x64 应用，24H2 起的仿真器 Prism 还支持 AVX、AVX2 等指令集扩展。仿真只覆盖用户态代码，桌面端不含内核驱动，可以整体在仿真下运行。代价是用不上 Arm 电脑上高通的神经网络处理器（Neural Processing Unit，NPU）：ONNX Runtime 调用高通 NPU 的执行提供程序基于高通的 AI Engine Direct 软件开发包（简称 QNN），只有 Arm64 原生版本。

### 1.2 macOS

macOS 版只支持 Apple 芯片，依据有三条：

- macOS 27 只支持 Apple 芯片的 Mac，Intel Mac 最高停在 macOS 26；通用的 Rosetta 转译只提供到 macOS 27；
- onnxruntime 1.31.0 和 PyTorch 2.14.1 的官方 macOS 安装包只有 Apple 芯片版本，PyTorch 从 2.3 起不再发布 Intel Mac 版本；
- 本机模型工具在 Intel Mac 上的加速受限，例如 Ollama 在 Intel Mac 上只能用 CPU 运行。

最低版本定为 macOS 15，需要测试的系统版本更少。系统自带的设备端翻译接口 TranslationSession 也从 macOS 15 开始提供，但在 macOS 15 上只能经 SwiftUI 界面取得翻译会话，首版不把它作为翻译服务，留到后续版本。

## 2 需求与系统能力对照

下表列出每项依赖桌面接口的需求，以及两个平台提供的对应能力。

| 需求 | Windows | macOS |
| --- | --- | --- |
| 屏幕采集 | Windows.Graphics.Capture；桌面程序可以直接按显示器或窗口建立采集，不经系统选择器 | ScreenCaptureKit，macOS 12.3 起 |
| 采集排除平台自己的全部窗口 | 每个窗口通过 `SetWindowDisplayAffinity` 设为 `WDA_EXCLUDEFROMCAPTURE` | 采集时用 `SCContentFilter` 按应用排除本应用，之后新建的窗口也自动排除 |
| 采集不含鼠标指针 | Windows.Graphics.Capture 的 `IsCursorCaptureEnabled` | `SCStreamConfiguration.showsCursor` 设为 false |
| 覆盖层让鼠标和键盘穿透 | 分层窗口（`WS_EX_LAYERED`）加 `WS_EX_TRANSPARENT`，鼠标事件全部交给下方窗口；加 `WS_EX_NOACTIVATE` 后不会成为前台窗口，键盘输入留在用户正在操作的窗口 | 覆盖层窗口设置 `ignoresMouseEvents`；无边框窗口不会成为接收键盘输入的窗口 |
| 浮卡和鼠标旁提示不抢焦点 | `WS_EX_NOACTIVATE`；浮卡要响应拖动时，在 `WM_MOUSEACTIVATE` 中返回 `MA_NOACTIVATE`，照常收到鼠标消息但不被激活；`WS_EX_TOOLWINDOW` 让它们不出现在任务栏和 Alt+Tab 中 | 使用不激活应用的面板（`nonactivatingPanel`） |
| 覆盖层盖在其他应用的全屏画面上 | 置顶窗口（`WS_EX_TOPMOST`），真正的独占全屏游戏除外，见 2.2 | 需要菜单栏应用形态，见第 3 节 |
| 覆盖层跟随目标窗口移动 | `SetWinEventHook` 订阅窗口位置变化事件（`EVENT_OBJECT_LOCATIONCHANGE` 等），进程外回调，不需要权限 | 读取窗口坐标（`CGWindowListCopyWindowInfo`），不需要权限 |
| 被其他窗口挡住的部分不显示译文 | `SetWindowPos` 把覆盖层排在目标窗口正上方，见 2.1 | 覆盖层留在上层，按挡在目标窗口前面的其他应用的窗口（`optionOnScreenAboveWindow`）裁掉被挡住部分的译文和暗化层，见 2.1 |
| 跟随活动窗口 | `SetWinEventHook` 订阅前台窗口变化（`EVENT_SYSTEM_FOREGROUND`），不需要权限 | 订阅 `NSWorkspace` 的应用激活通知，再从 `CGWindowListCopyWindowInfo` 取前台应用最靠前的普通窗口，不需要权限 |
| 取词 | UI Automation 的 TextPattern 读取选区；取不到时模拟 Ctrl+C 再读剪贴板，见 4.1 | 辅助功能接口读取选中的文字，需要辅助功能权限，见 4.2 |
| 全局快捷键 | `RegisterHotKey`，不需要权限 | `RegisterEventHotKey`，不需要权限 |
| 后续版本：点击鼠标或按键时截屏；选中文字后自动弹出按钮 | 低级键盘鼠标钩子或 Raw Input，不需要权限；以管理员身份运行的程序在前台时，低级钩子收不到输入，见 4.1 | 监听键盘需要输入监控权限，见 4.2 |
| 缩放比例不同的多块显示器 | 声明每显示器 DPI 感知 V2，采集坐标和窗口坐标统一为物理像素 | 按每块显示器的缩放比例，在像素和点之间换算 |

### 2.1 遮挡的处理方式

两个平台处理遮挡的方式不同，效果相同：被其他窗口挡住的部分既不显示译文，也不压暗挡在前面的窗口，见 [产品需求](01-product.md) 5.2。

Windows 上，`SetWindowPos` 的 `hWndInsertAfter` 参数指定排在被定位窗口前面的窗口，覆盖层可以借此排在目标窗口正上方。目标窗口被激活、提到最前后，覆盖层要重新排序。微软 PowerToys 的"始终置顶"也用 `SetWindowPos` 让自己的边框窗口跟随目标窗口的位置和层级。

macOS 没有官方支持把窗口排在别的应用的窗口正上方：Apple 文档和员工回复都没有给出支持，目标应用被激活时，它的窗口还会盖住覆盖层。所以 macOS 上覆盖层留在上层，按其他应用窗口的遮挡区域，裁掉这部分的译文和暗化层。

### 2.2 Windows 上的全屏游戏

游戏以真正的独占全屏运行时，独占显示输出，外部覆盖层不能稳定地叠在上面。Windows 10 起的全屏优化让多数以为自己在独占全屏的游戏实际以无边框方式运行，这时由桌面窗口管理器把覆盖层叠在游戏画面上。用户在程序属性里为某个游戏关闭全屏优化后，这个游戏回到真正的独占全屏，覆盖层不保证能显示。

## 3 应用形态

两个版本都以常驻图标的形式运行：Windows 版做成系统托盘应用，主窗口从托盘图标打开；macOS 版做成菜单栏应用，不显示 Dock 图标，功能入口放在菜单栏图标里。持续屏幕运行时，两个版本都不占用任务栏或 Dock。

macOS 版不显示 Dock 图标，是覆盖层能叠在其他应用全屏画面上的前提。Apple 技术支持说明，普通前台应用的窗口不会叠到其他应用的全屏空间之上；要做到这一点，需要同时满足三个条件：

1. 应用以辅助应用方式运行，不显示 Dock 图标；
2. 覆盖层和浮卡使用不激活应用的面板；
3. 窗口处于屏幕保护程序层级。

全屏阅读文档、看漫画、玩游戏都属于持续屏幕的主要场景，所以 macOS 版采用这种形态。

## 4 系统权限与限制

### 4.1 Windows

Windows 不要求用户逐项授权，但用户界面特权隔离（User Interface Privilege Isolation，UIPI）限制普通权限的程序操作以管理员身份运行的程序。以管理员身份运行的程序在前台时：

- UI Automation 访问不到它的界面，读不到选中的文字；
- 模拟按键会被拦截，调用方从返回值上看不出按键没有送达；
- 低级键盘鼠标钩子收不到输入；
- 全局快捷键不受影响。

绕过这项限制的官方途径是 UIAccess，微软要求非辅助技术类应用不要使用；桌面端也不以管理员身份运行。所以对以管理员身份运行的程序，划词和后续版本的按键触发截屏不可用，桌面端在这种情况下提示原因。

UI Automation 取不到选区时，取词退而模拟 Ctrl+C 再读剪贴板。这条退路有两个代价：

- 用户开启了剪贴板历史时，复制的文字会进入历史；开启了跨设备同步时，还会同步到同一账户的其他设备；
- 其他监听剪贴板的程序都会收到这次变化。

### 4.2 macOS

macOS 的屏幕采集、取词和输入监听都要用户在"系统设置 > 隐私与安全性"中逐项授权：

| 权限 | 用途 | 没有授权时 |
| --- | --- | --- |
| 屏幕与系统录音 | 单次截图、持续屏幕、图片问 AI 的屏幕画面 | 这几项功能不可用 |
| 辅助功能 | 取词；取词失败时模拟 Cmd+C | 划词不可用 |
| 输入监控 | 后续版本的按键触发截屏 | 只能使用定时触发 |
| 本地网络 | 连接局域网中的地址：部署在家庭电脑或 NAS 上的后台、局域网里的 AI 服务、自定义 HTTP 请求的目标；macOS 15 起需要 | 这些连接全部失败 |

桌面端对这些权限的要求：

- 首次使用某项功能前，说明它需要哪项权限、用来做什么，并引导用户打开对应的设置页；
- 没有授权的功能明确提示原因，其余功能照常使用；
- 屏幕录制权限授予后，要重启桌面端才能开始采集，桌面端需要提示用户重启。

macOS 上的取词还有三个已知限制：

- Chromium 系浏览器和 Electron 应用默认不暴露网页内容的无障碍信息，要先让它们开启无障碍模式，才能读到选中的文字；
- 取词失败时可以退而模拟 Cmd+C 再读剪贴板，模拟按键同样需要辅助功能权限。Apple 已经宣布，程序主动读取剪贴板时系统会提醒用户，相关接口从 macOS 15.4 起提供；
- 任何程序开启安全输入时，例如用户正在输入密码，其他程序的键盘监听都收不到按键，按键触发截屏在这段时间里失效。

### 4.3 macOS 的定期录屏确认

macOS 15 起，不经系统内容选择器、直接采集屏幕的应用，会被系统定期要求用户再次确认。macOS 15.0 为每月一次，15.1 起系统对常用的应用减少提示，macOS 26 上这个提示仍然存在。能避开它的只有两条路：经系统选择器采集，或者使用只发给远程桌面类应用的持久内容采集权利。

桌面端采用直接采集，接受这个定期确认。理由是系统选择器只能选窗口、应用或整块显示器，做不到跟随活动窗口，每次开始还要用户手动选择；单次截图和跟随活动窗口不经选择器，无论如何都会触发确认。

桌面端需要在说明中告诉用户这个提示从哪里来、点"允许"之后采集会继续。受管理的设备可以由管理员通过移动设备管理（Mobile Device Management，MDM）的 `forceBypassScreenCaptureAlert` 关闭这个提示，macOS 15.1 起有效。

## 5 采集时的系统提示与中断

### 5.1 Windows 的采集边框

Windows.Graphics.Capture 采集时，系统在被采集的窗口或显示器周围画一圈黄色边框。Windows 11 上，应用可以请求去掉边框，这需要征得用户同意，管理员也可以用组策略统一允许或禁止。

桌面端在 Windows 11 上请求去掉边框；用户或策略拒绝时，边框照常显示，采集不受影响。

### 5.2 macOS 的屏幕共享指示

macOS 14 起，每个屏幕采集都显示在菜单栏的屏幕共享指示里，用户可以随时在那里结束采集。持续屏幕运行因此要处理来自平台之外的中断，规则见 [运行与生命周期](04-run-lifecycle.md) 8.3。

## 6 两个平台无法消除的差异

| 差异 | Windows | macOS |
| --- | --- | --- |
| 其他录屏软件能否录到覆盖层 | 录不到：`WDA_EXCLUDEFROMCAPTURE` 对所有屏幕采集都生效 | 录得到：没有公开接口能阻止其他程序采集，`NSWindow.sharingType` 的 `.none` 已是系统不再使用的旧常量 |
| 系统权限 | 不需要逐项授权；以管理员身份运行的程序在前台时，划词和按键监听失效 | 需要逐项授权，见 4.2 |
| 采集时的系统提示 | 黄色边框，Windows 11 上可以请求去掉 | 菜单栏的屏幕共享指示，以及定期录屏确认 |
| 覆盖层盖在全屏画面上 | 置顶窗口即可，真正的独占全屏游戏除外 | 需要菜单栏应用形态 |
| 遮挡的处理 | 覆盖层排在目标窗口正上方 | 覆盖层留在上层，裁掉被挡住的部分 |

第一项是两个平台机制的直接结果：Windows 的排除设置作用于所有采集方；macOS 只能由采集方自己排除，平台自己的采集排除了覆盖层，别的程序照样能录到。用户需要让别人看到带译文的画面时，在 Windows 上要用平台自己的网页观看，在 macOS 上用其他录屏软件也可以。

## 7 两个平台共同的限制

- 只采集某个窗口时，采不到这个应用弹出的菜单、下拉框和工具提示。Windows 的窗口采集默认不含次级窗口，Windows 11 24H2 起可以选择包含与主窗口相交的部分；macOS 的单窗口采集不含弹出窗口和子窗口。需要翻译菜单时，改用区域或整屏范围。
- 取词会让 Chromium 系浏览器和 Electron 应用开启无障碍模式。Electron 文档提示，渲染无障碍树会显著影响应用性能。

## 8 安装与分发

### 8.1 Windows

Windows 版只发布签过名的安装包，不上架 Microsoft Store：

- 安装包用组织验证（Organization Validation，OV）代码签名证书签名。没有签名的程序从网上下载后运行时，SmartScreen 会拦下，用户要点"仍要运行"；
- 从 2024 年起，扩展验证（Extended Validation，EV）证书也不再能直接获得 SmartScreen 信誉，OV 和 EV 都要靠下载量积累。微软估计需要数周时间和数百次正常安装；
- 始终用同一个签名身份发布，新版本可以继承已经积累的信誉；
- 2023 年 6 月起，OV 证书的私钥必须存放在硬件安全模块或硬件令牌里，签名流程要按 USB 令牌或云端硬件安全模块来规划。微软的 Artifact Signing 服务不对中国大陆和中国香港的组织或个人开放；
- 安装包里附带的原生库，例如推理库，同样要签名。Windows 11 的智能应用控制开启时，会拦截没有签名、也没有正面信誉的程序和二进制文件。

### 8.2 macOS

macOS 版在 Mac App Store 之外分发，使用 Developer ID 签名并经过 Apple 公证：

- 不上架 Mac App Store：Mac App Store 应用必须启用 App 沙盒，沙盒禁止辅助类应用使用辅助功能接口，取词无法实现；
- 签名和公证需要加入 Apple Developer Program，年费 99 美元。从 macOS 10.15 起，2019 年 6 月以后构建、用 Developer ID 分发的软件都必须公证；
- 固定使用同一个签名身份。系统按代码签名判断新旧版本是不是同一个程序，换了签名身份，用户之前给的授权全部失效；
- 需要系统权限的系统集成服务打包在签过名的 .app 里。macOS 26.1 上，不在 .app 中的可执行文件申请屏幕录制权限后，不会出现在授权列表里，用户无法查看或撤销；
- 随桌面端安装的本机处理服务和第三方库，与主程序使用同一个开发者身份签名。强化运行时默认只允许加载 Apple 签名或同一开发者身份签名的库。

### 8.3 自行编译的版本

用户从源代码自行编译、没有签名的版本也能运行，但要承担以下代价：

- Windows 上，SmartScreen 会拦下运行，用户要点"仍要运行"；开启了智能应用控制的电脑会直接拦截；
- macOS 15 起取消了按住 Control 点按"打开"的绕过方式，用户要先尝试打开，再到"系统设置 > 隐私与安全性"里点"仍要打开"；
- macOS 上，每次重新编译后，系统都把它当作新程序，屏幕录制、辅助功能等授权要重新给一遍。
